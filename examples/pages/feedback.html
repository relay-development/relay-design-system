システムフィードバックのアクセシビリティ

guideline

保存できた・送信に失敗した・削除してよいか、といった操作に対するシステムの返答を、誰にも同じように届ける方法をまとめたガイドです。relay では返答の置き場所を 4 つに決め、画面の隅に出て数秒で消えるトースト／スナックバーは意図的に用意していません。その理由と、代わりに何を使うかを説明します。

3 つの原則

フィードバックが届かない典型は「見ていない場所に出た」「読む前に消えた」「読み上げられなかった」の 3 つです。原則はその裏返しです。

1. 操作した場所に置く

利用者の視線は押したボタンや入力欄にある。返答はその視野の中、DOM 上もその要素の直後に置く。拡大表示や読み上げでも「何の結果か」がつながる。

2. 利用者のペースで消える

時間で勝手に消さない。消えるのは次の操作をしたとき、または利用者が閉じたとき。読むのに時間がかかる人、画面から目を離していた人にも届く。

3. 色に頼らず、支援技術にも伝える

アイコン＋文言で意味を運び、テーマと文言を一致させる。動的に出す返答は role="status"／role="alert" でフォーカスを奪わずに読み上げる。

返答の置き場所は 4 つに決める

「どこに置くか」と「どう消えるか」で選びます。見た目の好みで選ばず、状況から機械的に決められるようにしています。GitHub Primer が Toast を持たず Banner / InlineMessage / Dialog に振り分けているのと同じ整理です。

トースト／スナックバーを意図的に置いていない理由

画面の隅に固定して数秒で消える通知は、Material Design ではスナックバー、Android ではトーストと呼ばれ、Web でも広く使われています。relay はこれをコンポーネントとして用意しません。便利に見えますが、仕様そのものが次の達成基準と衝突し、DS 側で作ると違反の入口を配ることになるからです。

衝突する達成基準（WCAG 2.2）

基準 トーストで起きること relay の置き方で解けること
2.2.1 タイミング調整可能 数秒で消えるため、読むのに時間がかかる人・目を離していた人は内容を知れない。延長や停止の手段を全通知に付けるのは現実的でない 次の操作まで残す。時間制限そのものを作らない
1.3.2 意味のある順序 DOM の末尾に挿入されるので、読み上げ順では「どの操作の結果か」が切れる 操作した要素の直後に挿入し、視覚と読み上げの順序を一致させる
2.4.3 フォーカス順序 ・ 2.1.1 キーボード アクション付きトーストは、消える前にキーボードで到達するのが難しい。到達させるためにフォーカスを飛ばすと作業が中断される 操作直近にあるので Tab 1 回で届く。フォーカスは動かさない。判断が要るなら modal でフォーカスを預かり、閉じたら戻す
4.1.3 ステータスメッセージ 読み上げ自体は aria-live で可能だが、消えた後に聞き返す手段がない 残っているので、いつでも読み直せる
1.4.10 リフロー ・ 1.4.4 テキストのサイズ変更 画面隅に固定されるため、400% ズームやスクリーン拡大鏡で操作対象を見ている利用者の視野に入らない。拡大するとコンテンツを覆う 操作対象と同じ視野に置くので、拡大しても一緒に見える

基準の外でも起きる問題

達成基準に直接は当たらないが、フィードバックが届かなくなる要因

  • !見逃し — 隅に出る小さな通知は、繰り返し見るうちに広告のように無視されるようになる（バナー盲）。本当に伝えるべき失敗も同じ扱いで流れる
  • !誤って閉じる — スワイプや近くのタップで意図せず消える。「元に戻す」のようなアクションを載せると、消えた時点で取り消しの機会も失われる
  • !重要度の混在 — 成功も失敗も同じ位置・同じ見た目で流れるため、重大なエラーが「いつもの通知」に埋もれる
  • !実装の分岐 — 表示時間・キュー・スタック・アクション・閉じるボタンの有無がプロダクトごとに揺れ、DS で見た目を揃えても振る舞いが揃わない

同じ理由で GitHub Primer は Toast を持たず、アクセシビリティガイドで「Toasts pose significant accessibility concerns and are not recommended for use」と明記しています（Primer: Toasts）。

「それでもトーストが要る」と思ったときの読み替え

トーストを使いたくなる場面は、たいてい次のどれかに置き換えられます。

やりたかったこと 読み替え
保存・送信の成功を知らせたい 結果が画面で分かるなら出さない。分からないなら「保存する」の横に inline-message（success）を残す
通信エラーを知らせたい 操作した場所に inline-message（negative・role="alert"）。再読み込みや再ログインが必要なら modal で止める
「元に戻す」を数秒だけ出したい 取り消し導線を時間制限つきにしない。削除前に modal で確認するか、削除後に alert で「元に戻す」を残す
別画面に遷移した後に結果を知らせたい 遷移先の上部に alert（success）を常設で置く。利用者が閉じるまで残す
時間のかかる処理の完了を知らせたい 処理中は操作した場所で進行を示し、完了は同じ場所に inline-message か、一覧なら該当行の状態として表す。画面を離れる長さならメールなど画面外の手段も検討する
同時に複数の結果を知らせたい スタックさせない。それぞれの操作直近に置くか、ページ上部の alert に要約して箇条書きにする

実装チェックリスト

コンポーネントを選んだあと、プロダクト側で確認する項目です。各コンポーネントの「アクセシビリティ」タブと MCP get_component の同名の節にも同じ内容があります。

置き場所と順序

  • !操作した要素の直後に、視覚上も DOM 上も挿入している
  • !position: fixed で画面隅に固定していない
  • !フォーカスを動かしていない（modal を除く。modal は閉じたら呼び出し元へ戻す）
  • !400% ズームで操作対象とメッセージが同じ視野に入る

消え方

  • !setTimeout 等で自動消去していない
  • !消えるのは次の操作か、利用者の明示的な操作（閉じる・修正・再送信）のとき
  • !閉じるボタンがあるなら aria-label="閉じる" があり、キーボードで到達できる
  • !取り消し（元に戻す）に時間制限を付けていない

支援技術への通知

  • !動的に出す結果に role="status"（成功・情報）／role="alert"（失敗・注意）がある
  • !ライブリージョンは空の状態で先に置くか、挿入と同時に role を持つ要素として追加している（後から role だけ付けると読み上げられない）
  • !同じ内容を短時間に繰り返し挿入していない（読み上げが連続する）
  • !modal は showModal() で開き、aria-labelledby でタイトルを名前にしている

意味の伝え方

  • !テーマ（success / negative / warning）と文言が一致している
  • !アイコンは aria-hidden="true"、意味は文言が運ぶ
  • !失敗の文言に「何が起きたか」と「次に何をすればよいか」がある
  • !グレースケール表示でもアイコンと文言で意味が分かる
