# eval-report — evals の HTML レポート生成と読み方

## 手順

1. **生成**: `npm run eval:report:html`（直近 20 実行。全履歴は `-- --all`）
   → `evals/results/report.html` に出力される（gitignored。決定的生成なので何度でも作り直してよい）
2. **読む順番**:
   - 見出しの R/C 集計（regression は 100% 維持が前提、capability は改善メーター）
   - 履歴推移マトリクスで**変化した列**（✓→✗ / ✗→✓）を探す
   - 最新実行のお題別カード — FAIL したトライアルは自動で展開されている
3. **所見をユーザーに報告する**。形式は自由だが、次を必ず含める:
   - 変化（✓→✗ / ✗→✓ / 変化なし）を先頭に
   - fail は 3 方向で切り分ける — **知識 / 採点基準 / お題**。分水嶺は「正しい知識を持った理想のエージェントなら安定して合格できるか」（Yes なら知識か基準、No ならお題）。最終判断はユーザーに委ねる
   - **✗→✓ の改善も鵜呑みにしない** — 行動ログでメカニズム（どの経路で知識に到達したか）を確認してから改善と報告する（見かけの改善の除外）
   - ✓→✗ は劣化と断定する前に `--case <id> --trials 2` での再確認を提案（生成ブレの可能性）

## 深掘りの観点（シーケンス表で探すもの）

- **空振り**: search 等の応答が極端に小さい行（例: 134 字の「ヒットなし」）→ 語彙・誘導の穴
- **巨大応答**: 突出して大きい応答 → 知識の一括返しすぎ（topic 分割等の余地）
- **突合の ✗**: get_component で引いたのに最終 HTML で未使用 → 知識と期待の衝突の可能性（過去の実例: button を引いた上で当時のルールに従い link を選んでいた）
- 生ログは `evals/results/outputs/<実行スタンプ>/<id>.transcript.jsonl`。エージェントの発話も証拠になるが、必ずツール呼び出しの事実で裏取りする

## 共有

- ユーザーに求められたら、report.html を Artifact として公開する（favicon は 📊 で固定。同じファイルパスで再公開すれば URL は維持される）
- レポートは自動生成の事実のみ。所見・切り分けはチャットで添える（レポートに手書きで混ぜない）

## 注意

- このスキルが実行するのはレポート**生成**のみ（無料）。eval の**実行**（`npm run eval`）は LLM を消費するため、必ずユーザーに確認してから
- レポートの実装は [evals/report-html.mjs](../../../evals/report-html.mjs)。表示項目を足すときはそちらを編集（transcript 解析は evals/transcript.mjs を共用）
